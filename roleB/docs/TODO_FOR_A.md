`cron`을 더 촘촘히 해도 해결되지 않는다. GitHub의 스케줄 큐 지연은 알려진 동작이고,
저활동 레포일수록 심하다.

### 지금 당장 (발표용)

**발표 직전에 Actions → `Poll Seoul Citydata` → `Run workflow`를 직접 누른다.**
한 번에 스냅샷 3회가 들어오고 신선도 기준이 90분이라 시연 직전 한 번이면 충분하다.
**리허설 때도 매번 누른다.**

### 제대로 고치려면 (발표 후여도 된다)

외부 스케줄러가 GitHub API로 `workflow_dispatch`를 때리는 방식이 확실하다.
무료 스케줄러(cron-job.org 등)에서 15분마다:

```
POST https://api.github.com/repos/sohee-log/Dacos_WhereToGo/actions/workflows/poll-citydata.yml/dispatches
Authorization: Bearer <PAT · actions:write>
Body: {"ref":"main"}
```

**확인하는 법**

```powershell
cd roleB
$env:DATABASE_URL = "<DSN>"
python -m tools.check_data_readiness   # "최근 스냅샷 N분 전"이 90 이하면 초록
```

**이게 없으면 무엇이 죽나** — `live_segment_match`(0.10) + `crowd_fit`(0.08) =
**0.18이 "실시간"이 아니게 된다.** 배너의 "지금 여유 → 22시 붐빔"이 세 시간 전
값이고, 화면으로는 구분이 안 된다. 차별점 1번이 사실상 잠긴다.

## 🟡 A-10 `outdoor_exposure` 관측 17.4% — 차별점 2번이 잠겨 있다

T1 800건 중 139건만 관측됐다. 나머지는 NULL이고, 엔진은 이를 중립으로 접는다
(순위를 왜곡하지는 않는다 — `OUTDOOR_EXPOSURE_UNKNOWN`).

**그런데 `context_fit`의 실제 기여가 설계 13% 대비 4.0%까지 내려간다.**
후보 다섯 중 넷이 같은 값이라 순위를 못 가르는 것이다
([`WEIGHT_TUNING.md`](WEIGHT_TUNING.md) 근거 ①).

즉 **"비가 와서 실내 위주로 골랐습니다"가 근거를 갖는 POI가 다섯에 하나뿐**이다.
가중치로는 못 고친다 — 올려도 없는 관측이 생기지 않는다. 관측률이 오르면
그때 가중치를 다시 본다.

발표 전에 손댈 수 있다면 **T1 상위(추천에 자주 뜨는) POI만이라도** 야외 여부를
채우는 것이 가성비가 가장 좋다. 전량이 아니어도 된다.
