# WhereToGo

비가 오면 갈 곳이 바뀐다.

WhereToGo는 서울 용산구를 대상으로, 지금의 날씨와 혼잡도, 그리고 사용자의 나이·성향·목적에 맞는 장소를 찾아준다. 평점 높은 순으로 나열하는 대신 *"지금 이 상황에서 당신 같은 사람이 실제로 가는 곳"* 을 판단한다.

---

## 왜 만드는가

지도 앱에서 "이태원 카페"를 검색하면 평점 4.5 이상이 백 곳쯤 나온다. 그 목록은 **비 오는 화요일 저녁에 네 명이 갈 만한 곳**을 알려주지 않는다.

실제로 사람이 어디를 갈지는 몇 가지가 함께 정한다. 날씨, 미세먼지, 요일과 시간, 함께 가는 인원, 그날의 목적. 그리고 같은 조건이라도 스물여덟 살과 마흔다섯 살의 선택은 다르다.

WhereToGo는 이 조건들을 한 번에 넣고 답을 낸다.

```
입력   28세 · 여성 · 데이트 · 2명 · 예산 3만원대 · 이태원 · 오늘 19시
상황   비 70% · 체감 26° · 이태원 지금 약간 붐빔 → 19시 붐빔 예상

출력   1. ○○○  (430m)  실내 · 조용함
          비 예보가 있어 완전 실내 공간 위주로 골랐습니다.
          20대 후반의 이 시간대 방문 비중이 높은 곳입니다.
          "비 오는 날 창가 자리에서 보는 뷰가 좋아요"
```

추천마다 **왜 이곳인지**를 실제 후기 문장과 함께 보여준다. 이유를 말할 수 없는 추천은 내보내지 않는다.

## 어떻게 동작하는가

네 단계를 거친다. 각 단계는 앞 단계보다 열 배 비싸고 열 배 적은 대상을 처리한다.

```
후보 생성    수백 개    반경 · 영업시간 · 인원 · 날씨 하드필터        SQL
   ↓
스코어링     상위 20    세그먼트 · 목적 · 취향 · 날씨 · 혼잡 · 품질    산술
   ↓
근거 검색    최종 3~5   리뷰 벡터 검색 후 인용 · 설명 생성            LLM
   ↓
로깅         전량       노출 · 클릭 · 선택 기록
```

### 설계에서 중요했던 결정 세 가지

**개인 방문 기록 없이 개인화한다.**
"비슷한 사람들이 많이 간 곳"을 찾으려면 보통 협업 필터링을 쓰지만, 개인 단위 방문 로그는 공공에 없고 서비스 초기에는 자체 로그도 없다. 대신 서울시 상권분석 데이터가 상권 × 업종 × 성별 × 연령 × 요일 × 시간대로 소비를 집계해 둔 것을 쓴다. 개인 정보 없이도 "금요일 저녁 이태원 카페에 20대 후반이 얼마나 몰리는가"를 계산할 수 있다.

**지역을 먼저 고르지 않는다.**
동네를 정한 뒤 그 안에서 장소를 찾으면 경계 바로 밖의 더 나은 후보를 영영 놓치고, 첫 단계가 틀렸을 때 복구할 방법이 없다. 처음부터 장소 단위로 후보를 뽑고, 상권의 인기도는 점수의 한 항으로만 반영한다.

**리뷰는 미리 읽어둔다.**
요청이 올 때마다 수백 개의 리뷰를 언어 모델에 넣으면 응답이 십 초를 넘고 비용도 감당이 안 된다. 리뷰는 배치로 미리 읽어 야외 노출도, 단체석 여부, 소음 수준, 웨이팅 강도 같은 구조화된 속성으로 바꿔 저장한다. 그러면 "4인 / 조용한 곳 / 비 옴"은 SQL 한 번으로 끝난다. 언어 모델은 최종 다섯 곳의 근거를 인용할 때만 부른다.

### 날씨를 다루는 방식

기온과 사람의 행동은 직선 관계가 아니다. 15도에서 25도 사이가 가장 활발하고 양쪽으로 갈수록 줄어든다. 미세먼지는 농도 수치보다 "나쁨" 등급이 발표되는 순간에 행동이 꺾인다.

그래서 모든 장소에 야외 노출도를 0에서 1 사이 값으로 매겨두고, 날씨 조건에 따라 이 값을 비선형으로 곱한다. 비가 오면 야외 좌석 중심의 장소가 후보에서 빠지고, 맑고 선선하면 오히려 가산점을 받는다.

또 하나. 사람은 지금이 아니라 **도착할 때**를 기준으로 결정한다. 그래서 실측값이 아니라 방문 예정 시각의 예보를 쓴다.

## 데이터

전부 공개 데이터이고 비용이 들지 않는다.

| 출처 | 쓰임 |
|---|---|
| 소상공인시장진흥공단 상가정보 | 장소 목록과 좌표 |
| 서울시 상권분석서비스 | 성별·연령·시간대별 소비 통계 |
| 서울시 실시간 도시데이터 | 날씨, 대기질, 실시간 혼잡도와 연령 구성, 12시간 예측 |
| 기상청 단기예보 | 세 시간 이상 뒤의 예보 |
| 네이버 검색 API | 방문 후기 텍스트 |
| 한국관광공사 TourAPI | 박물관·공원 등 비상업 시설 |
| 카카오 로컬 · 지도 SDK | 장소 정보 보정, 지도 |

지도 서비스의 리뷰는 크롤링하지 않는다. 약관을 위반하지 않는 경로만 쓴다.

별점 데이터가 없는 대신 세 가지로 품질을 판단한다. 블로그 언급량, 후기 논조에서 뽑은 감성 점수, 그리고 상권분석의 실제 매출. 협찬 글은 감성 집계에서 제외한다. 별점보다 조작에 덜 취약하다.

## 대상 지역

서울 용산구 전역. 한 구 안에 성격이 전혀 다른 생활권이 모여 있다.

이태원과 한남은 밤과 외국인, 이촌과 서빙고는 주거와 가족, 용산역과 한강로는 대형 실내 시설, 후암과 해방촌은 언덕과 로컬 감성. 같은 조건이라도 사람에 따라 다른 곳이 나와야 한다는 걸 보여주기에 좋은 지역이다.

남산과 한강, 경부선 철로가 생활권을 물리적으로 끊어 놓는다는 점도 중요하다. 직선거리로 800미터라도 철로 반대편이면 걸어서 20분이다. 그래서 거리를 잴 때 생활권 사이의 이동 저항을 배율로 반영한다.

## 기술

```
Next.js  ─────▶  FastAPI  ─────▶  PostgreSQL
 Vercel           Render          PostGIS + pgvector
                                     Supabase
                                         ▲
                                         │ 배치
                                   GitHub Actions
```

공간 질의와 벡터 검색을 한 데이터베이스에서 처리한다. 임베딩(bge-m3)은 서버에 올리지 않고 배치에서 미리 계산해 결과만 적재한다. 사용자 쿼리 조합이 유한하기 때문에 가능한 방식이고, 덕분에 무료 티어 안에서 벡터 검색이 돌아간다.

모든 구성 요소는 무료 티어를 쓴다. 결제 수단을 등록하는 서비스는 사용하지 않는다.

## 현재 상태

설계 완료. 구현 착수 전.

6주 일정으로 진행하며, 첫 주의 목표는 기능이 아니라 **빈 화면이라도 배포된 URL을 띄우는 것**이다. 배포에서 막히는 문제는 마지막 주에 발견하면 치명적이고 첫 주에 발견하면 사소하다.

| 주차 | 목표 |
|---|---|
| 1 | 스키마와 API 계약 확정, 배포 파이프라인 개통 |
| 2 | 용산 전역 장소 데이터 적재 |
| 3 | 후기 수집과 속성 추출 |
| 4 | 추천 동작 — 언어 모델 없이 |
| 5 | 근거 인용과 설명 생성 |
| 6 | 사용자 테스트와 튜닝 |

네 번째 주의 목표가 "언어 모델 없이"인 건 의도적이다. 그래야 언어 모델이 실제로 얼마나 기여하는지 잴 수 있고, 쿼터가 떨어져도 서비스가 죽지 않는다.
